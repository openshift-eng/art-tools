# ART Pipelines UI

This application lists ART tenant Pipelines and PipelineRuns from the live OpenShift cluster and Tekton Results. The Pipelines list shows each Pipeline's latest run, status, and time. The PipelineRuns list shows status, start time, and duration. Each Pipeline has a PipelineRuns tab with an exact Pipeline filter. Run detail opens on a Details tab with Pipeline navigation, status, timestamps, labels, and annotations, alongside Components, Logs, Events, Parameters, and Task runs tabs. It supports starting a Pipeline and rebuilding an earlier PipelineRun with edited parameters. The rebuild form uses the current Pipeline definition and fills missing run parameters from its current defaults. A rebuilt PipelineRun links to its source run from the header. Active logs follow cluster pod log streams and discover new task steps every two seconds; completed or pruned run logs load from cluster pods or Tekton Results. HTTP and HTTPS URLs in logs are clickable. The Events tab shows matching PipelineRun, TaskRun, and pod events from the cluster and polls every 10 seconds while the run is active. Cluster events may expire and are not archived by Tekton Results.

The interface uses a compact top navigation and supports light and dark themes. The theme button in the header saves the selection in browser storage; light is the default. The namespace selector keeps the current page and filters the list views. When a PipelineRun has the `art.openshift.io/parent-pipelinerun` label, its banner links to that parent run in the same namespace, including when the parent is archived in Tekton Results. A parent run's banner links to its triggered child runs. The child lookup uses a Kubernetes label selector for live runs and a Tekton Results label filter for archived runs, scoped to the parent's namespace and name. The label does not contain the parent's UID, so reusing a parent run name after pruning can make the relationship ambiguous.

## Incidents

The Incidents navigation page and shared announcement strip read from the `art-pipelines-incidents` ConfigMap. The backend reads `/etc/incidents/incidents.json` for each `/api/incidents` request, and the frontend refreshes incident data every 30 seconds. A slim yellow strip sits above the app header on every page and is visible to all app viewers. It shows open incidents that have **Show in banner** enabled, one at a time, and advances every eight seconds when there are several. Closing an incident removes it from the strip. The Incidents page keeps active, resolved, and deleted entries visible, including incidents with banner display disabled. Each incident supports a severity (`info`, `warning`, or `danger`), title, short banner message, status, start/update/close/delete timestamps, description, up to ten HTTP(S) links, a banner visibility setting, and timestamped incident history.

Members of the OpenShift `art-members` group can create, edit, close, and delete incidents in the UI. Delete marks an incident as deleted, keeps it visible in history, and records its delete time. Everyone can view the Incidents page, banner, and incident history. Admins can disable **Show in banner** when recording an incident that should remain on the Incidents page without being announced. Editing requires a short update note; create, close, and delete add automatic history entries. The **Incident history** disclosure is collapsed until opened. Changes are written to the incidents ConfigMap using the signed-in user's token; the UI checks the user's permission before showing management controls. A namespace-limited OAuth role scope permits access to this ConfigMap, while the RoleBinding limits actual management permission to `art-members`. The cookie name changes when the added scope rolls out so existing sessions sign in again and obtain the updated scoped token. Event timestamps are recorded in UTC and displayed in the viewer's local time. Add Slack threads or tickets as incident links so users can find the investigation details.

The ConfigMap-backed history retains at most 20 incidents and caps the serialized JSON at 900 KiB, below Kubernetes' 1 MiB ConfigMap data limit. Each incident retains its latest 50 history entries; older entries are dropped. When the incident count is exceeded, deleted incidents are pruned first, followed by the oldest resolved incidents. If all 20 entries are active, creating another incident returns a conflict until one is resolved or marked deleted. Writes that exceed the byte budget are rejected without saving; shorten incident details or remove old resolved/deleted incidents through the normal retention process. Retained history stays with its incident until that incident is pruned.

Update the live incident list with `oc edit configmap art-pipelines-incidents -n art-pipelines-ui`. The Argo CD Application ignores this ConfigMap's `data.incidents.json` field so live edits are not reverted by self-heal; other ConfigMap fields remain managed by Git. Projected ConfigMap updates become visible without restarting the Deployment. Use an empty `incidents` array to clear the banner and show the empty state. Missing incident files return an empty list; malformed JSON reports an unavailable incident feed, and invalid individual entries are logged and skipped.

The backend uses the OpenShift OAuth token forwarded by its sidecar. Kubernetes and Tekton Results enforce each user's namespace permissions. The app does not persist run data or user tokens. The OAuth client requests `user:info` and `role:art-pipelines-ui-scope:*`; the scope limits the token to the API operations in `01-oauth-scope.yaml` and does not grant access to Secrets. It does not grant users permissions they do not already have. To add a tenant namespace, update `PIPELINE_NAMESPACES` in the GitOps ConfigMap and restart the `art-pipelines-ui` Deployment so its environment reloads.

When the saved OAuth token expires, the UI validates the session against OpenShift and automatically starts a fresh sign-in, returning to the current page and run tab. A page refresh alone does not clear the proxy cookie. Authentication failures in run history and live logs use the same recovery flow. Permission errors and service outages remain visible as errors. If sign-in does not restore the session, requests stop and a **Sign in again** action allows an explicit retry. Unsent Start/Rebuild edits may be lost during sign-in; submissions are never replayed automatically.

The pod disables automatic service account token mounting. The OAuth proxy still needs an in-cluster Kubernetes client for OAuth discovery, so a projected service account token is mounted only in the proxy container. The backend mounts only the Kubernetes CA from `kube-root-ca.crt`. An ingress-only NetworkPolicy limits access to the proxy to the OpenShift router without restricting the app's outbound cluster API and Results requests.

Start and Rebuild omit `spec.timeouts`, allowing Tekton to apply the current cluster timeout defaults. Rebuilds do not copy the previous run's timeout settings.

Start and Rebuild name new `promote-assembly` runs `promote-assembly-<assembly>-<random suffix>`. For example, assembly `4.22.18` produces `promote-assembly-4.22.18-ql58s`; the default assembly produces `promote-assembly-stream-*`. The name uses the assembly submitted in the form, including edits during Rebuild. The assembly fragment is normalized to lowercase Kubernetes name characters while preserving version dots, and truncated to keep the name stem within 48 characters. An empty or unusable fragment falls back to `promote-assembly-*`. The assembly parameter passed to the pipeline retains its original value.

## PipelineHealth (Beta)

The `#/health` page shows a compact matrix of scan-rooted build chains, grouped by tenant, group, and assembly. A bookmarked tenant view uses `#/health?namespace=art-acm-tenant`. The read-only `/api/pipeline-health` endpoint combines live PipelineRuns and Tekton Results, deduplicating by UID with live data preferred.

The chain starts at `layered-products-scan` and follows `build-layered-products`, `olm-bundle-konflux`, and all triggered `build-fbc` targets. Parent labels and triggered-run annotations establish relationships; `art.openshift.io/rebuilt-from` connects retries by UID. The newest explicit retry supplies the effective stage result, while original attempts remain visible in recovery history. Green requires every stage and target to succeed. Dry runs, missing triggered runs, reused parent names, and missing stages cannot establish green health.

LP scan recovery keeps bundle runs under the original image-build run and FBC runs under the bundle run that supplied their inputs. Recovery runs link to the previous ART attempt with `rebuilt-from` and `rebuilt-from-name`; the requesting scan is recorded separately in `art.openshift.io/recovery-scan`. The scan records created recoveries in `art.openshift.io/recovered-<hash>` annotations, which do not create build-chain edges. Retries preserve the original attempt's full operator batch, and active parents or attempts defer recovery. Normal downstream triggers continue to use the current run as parent.

The scan resolves build records' `art_job_url` against its own cluster and namespace, reading live PipelineRuns first and Tekton Results for pruned parents and child history. Archive lookup uses the scan's `oc` credentials and the namespace's `openshift-service-ca.crt` ConfigMap; `RESULTS_API_URL` and `RESULTS_CA_FILE` can override the endpoint and CA file. The scan identity needs PipelineRun get/list access, Results record get/list access, and ConfigMap get access when no CA file is supplied. Archive failures preserve available live relationships and emit a warning. If no parent can be verified, recovery still runs, with `art.openshift.io/recovery-lineage=unresolved` and no parent label or retry claim; it cannot clear failures in an unrelated chain.

Recovery acceptance: fail a bundle or one FBC target, let a later scan recover it, and check both parent/child navigation and the original health chain. Confirm an active retry preserves the last completed result, a successful retry restores green only after all required stages and targets succeed, and prior failed attempts remain in history. Repeat with an archived original, a multi-operator batch, and force-release recovery. Confirm an unavailable archive or missing parent produces the documented warning and unresolved lineage where applicable.

The last completed chain supplies the group's health; current running work and the latest scan are shown separately. A failed chain that stops before FBC makes the group red. Successful scans without downstream builds do not overwrite a previous build result. Expand a row for FBC targets, recovery attempts, and the ten most recent build chains. Every run link opens the existing Details page with its UID, including archived runs. Incomplete source history is reported and prevents confirming a group's green result. The page refreshes every ten seconds with active work and every thirty seconds otherwise, pausing requests while the tab is hidden.

For acceptance in `art-acm-tenant`, confirm a failed image build is red despite a successful root scan and follow its failure link. Expand ACM 2.15 to inspect all FBC target statuses, and ACM 2.17 to inspect its linked image-build retries. Verify that a later scan without builds preserves E2E health, an active newer build preserves the last completed result, and a completed successful retry restores green while retaining earlier failures. Check light/dark themes, namespace switching, refresh, archived run navigation, and expired-session recovery. The automated health tests cover complete success, fan-out failure/running states, retries, missing/ambiguous relationships, dry runs, tenant isolation, and partial history.

Navigation links and detail tabs open in the current tab with an ordinary click. Use Ctrl-click on Windows/Linux, Command-click on macOS, middle-click, or the link context menu to open a new tab. Pipeline and PipelineRun rows also support modified clicks outside their links. The selected tenant is preserved in navigation URLs, including when opening another tab. Pipeline tabs use `tab=details|runs`; PipelineRun tabs use `tab=details|components|logs|events|parameters|tasks`, preserving archived run UIDs.

## Results fetching and autoscaling

Results record requests use `RESULTS_PAGE_SIZE`, defaulting to 1,000 records per page. The value must be an integer between 1 and 10,000; invalid values prevent backend startup. The backend follows every continuation token and fetches fresh archive and live data on each request. PipelineHealth polls ten seconds after a response completes while work is active and thirty seconds otherwise, pausing requests while the tab is hidden.

The Argo CD Deployment manifest sets `RESULTS_PAGE_SIZE=1000` in the app container's environment, so changing it rolls the pods. The app requests 100m CPU and 384Mi memory with a 1Gi memory limit. The OAuth proxy requests 50m CPU and 64Mi memory with a 256Mi memory limit. Four steady replicas reserve 600m CPU and 1.75Gi memory including the proxies; a rolling update can temporarily add one extra pod.

The Argo CD HPA manifest manages one to four replicas using the `app` container's metrics. It targets 70% CPU utilization relative to the 100m request and 700Mi average memory usage. The largest replica recommendation from either metric wins. Scale-up has no stabilization delay and uses Kubernetes' default policies. Scale-down has a five-minute stabilization window and removes at most one pod per minute. Memory scaling uses an absolute value, independent of the memory request. The HPA responds to sustained average usage; individual request spikes and shared Results service latency still require monitoring.

The Argo CD Application ignores the Deployment's `/spec/replicas` field and uses `RespectIgnoreDifferences=true` so syncs preserve HPA decisions. Sync the Application configuration before enabling the HPA. Keep the page size, resources, and HPA settings in the GitOps manifests. After merging backend changes, build the application from Git using the existing BuildConfig and let the ImageStream trigger roll out the new image.

Testing plan: run the backend suite, including multi-page Results fetching, health, authentication, and live-over-archive deduplication. Validate the Deployment, HPA, and Application with server dry runs. After rollout, measure Quay and all-tenant loads, peak memory, and sustained traffic from multiple browser sessions. Confirm fresh run states arrive through periodic polling, HPA metrics are available, replicas scale within one to four, and scale-down occurs when both metrics fall below their targets. Verify OAuth sessions across replicas and confirm an Argo sync preserves the HPA's replica count. Monitor memory, restarts, and Results latency.

## Development

The backend is in `backend/pipeline_ui`; install `backend/requirements.txt` and run `uvicorn pipeline_ui.app:app` from `backend`. The frontend is in `frontend`; run `npm ci` and `npm run build`. Browser requests need an OpenShift OAuth proxy in front of the backend.

Run backend tests from `backend` with `python -m unittest discover -s tests`. Run frontend request and authentication tests from `frontend` with `npm test`.

For timeout acceptance after deployment, rebuild a harmless test run with an older timeout and confirm the new run receives the current cluster default. Verify the source run's timeout remains unchanged.

## Pilot and promotion

The deployment manifests are managed in [GitLab art-config](https://gitlab.cee.redhat.com/hybrid-platforms/art/art-config/-/tree/main/argocd/project/art-pipelines-ui). For a new cluster, apply those manifests directly, leaving the Deployment until last. Once the Route exists, run `python3 art-cluster/pipelines/ui/bootstrap_oauth.py` from the art-tools repository root to create a dedicated OAuth client and namespace Secret. The client requests a role scope across tenant namespaces, which a service account OAuth client cannot request. The bootstrap script reuses existing credentials on subsequent runs and keeps them out of Git. Then apply the Deployment. Before enabling the Argo CD application on a new cluster, create the Route and run the same bootstrap script. Changing the proxy cookie name when narrowing scopes forces existing browser sessions to obtain the new scope.

Changing the requested scope does not erase earlier OAuth consent or revoke old access tokens. When migrating this client away from `user:full`, remove only `OAuthClientAuthorization` and `OAuthAccessToken` objects whose `clientName` is `art-pipelines-ui`, then have users reopen the UI and approve the narrower request. This is a one-time migration; do not delete authorizations or tokens for other clients.

The BuildConfig's Git `contextDir` is `art-cluster/pipelines/ui`. To build unmerged local code safely, stage only the `ui` directory under that same relative path in a temporary directory, excluding `node_modules` and `dist`, then run `oc start-build art-pipelines-ui -n art-pipelines-ui --from-dir=<staging-root> --follow`. After the application code is merged into `openshift-eng/art-tools:main` and any manifest changes are merged into GitLab art-config, build from Git with `oc start-build art-pipelines-ui -n art-pipelines-ui --follow`. On a new cluster, create the [Argo CD Application from art-config](https://gitlab.cee.redhat.com/hybrid-platforms/art/art-config/-/blob/main/argocd/apps/art-pipelines-ui.yaml) to adopt the same resources. The Deployment follows the `art-pipelines-ui:latest` ImageStreamTag; a successful new build updates its image automatically. Argo CD ignores that image field so a sync does not roll it back.

## Component results

New `build-layered-products`, `olm-bundle-konflux`, and `build-fbc` runs publish version 1 JSON build reports in `art.openshift.io/component-build-<hash>` annotations, with a reporting marker in `art.openshift.io/component-report`. The run detail API reads these from both live resources and Tekton Results. This UI change can be deployed before the ART tools reporting change; older runs display “Component build results were not recorded”. Rebuilds start with fresh reports.

The Components tab lists component names, build results, and Konflux build PipelineRun links for both successful and failed builds. Every triggered build attempt keeps its own link and status. Search by component name or filter by build result. “Has failed attempts” also includes successful components with earlier failed builds; the Failed filter shows the final component result. The latest native build attempt supplies the component result; EC, ITS, and releases are outside this view. Reused, skipped, and dry-run builds remain distinct, with no fabricated PipelineRun links. Unfinished build results become Unknown after the ART run ends. Reporting or annotation capacity failures display an incomplete-report warning. No Konflux credentials or additional browser/API queries are required.

Testing plan: run the backend component and run detail suites, frontend tests, and `npm run build`; inspect fresh successful and failed builds of each pipeline, retry links and failed-attempt filtering, zero/missing attempt labels, live updates, archived results, preparation failures, reuse, dry runs, and rebuild isolation. Confirm later check/release failures do not change native build results.
